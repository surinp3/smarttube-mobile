# SmartTube Pat: self-hosted sync on your VPS

This replaces Bunny infrastructure with a small **Node 24 + SQLite** service.
The phone and Google TV apps keep the existing private pairing protocol. No
Supabase, Bunny account or database cloud service is required.

## What it handles

- Phone authorization with a private setup code and 10-digit TV pairing.
- Rumble follows, watched position, sidebar order and YouTube/Rumble/Both mode.
- Rumble browsing and playback. Known videos use Rumble's public embed player
  for playback. The optional VPS-only **API.SH** key covers discovery that
  Rumble's website blocks and older video URLs without an embed ID.
- Conflict protection when the phone and TV edit data at the same time.

Your existing signed-in YouTube account and subscriptions still communicate
with YouTube; this server stores no YouTube or Google login tokens.

## Deploy (once the VPS address and reverse proxy are known)

Requirements: Docker Engine + Docker Compose plugin, a DNS name directed at
the VPS, and HTTPS provided by the VPS's existing reverse proxy or Caddy.

1. Clone this repo on the VPS and enter `smarttube-mobile/vps-sync`.
2. Copy `.env.example` to `.env` and set a new private
   `SMARTTUBE_SETUP_CODE` of at least 20 random characters. For example,
   generate a code with `openssl rand -hex 32`. Keep the code out of GitHub
   and out of chat; enter it only into the **phone** during initial setup.
3. Set the optional `APISH_KEY` in `.env` for fallback Rumble discovery and
   legacy video URLs. Keep the key on the VPS.
4. Run `docker compose up -d --build` from this folder. The container uses a
   durable named volume for SQLite and exposes port 8765 **only on the VPS's
   loopback interface**.
5. Configure an existing Nginx, Caddy or Traefik reverse proxy to forward
   `https://<your-sync-domain>/` to `http://127.0.0.1:8765`. A simple Caddy
   example is in `Caddyfile.example`. HTTPS is mandatory for Android clients.
6. Verify `https://<your-sync-domain>/health` returns an HTTP 200 JSON object
   with `ok: true`. Test the phone bootstrap and TV code pairing before
   enabling remote sync in both apps.
7. Update the repository's public `sync_config.json` to
   `{"enabled":true,"edgeScriptUrl":"https://<your-sync-domain>"}`.
   **The field name `edgeScriptUrl` is a legacy client setting**, not a Bunny
   requirement. Mobile v14 and TV v3 currently read this field. We can rename
   the UI/config in a new signed APK release once the VPS endpoint is verified.

### Keep users' app data safe

Do not delete `smarttube_data`, run `docker compose down -v`, or remove the
Docker volume to redeploy. The SQLite file and WAL live in that volume.
The setup code is only needed on a new phone. After successful bootstrap,
each device has its own random token in private app storage.

Back up the volume before changing versions. A consistent SQLite backup can
be generated by running the following command inside the running container:

```sh
docker compose exec -T smarttube-sync node -e 'const {DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/data/smarttube.sqlite");d.exec("VACUUM INTO /data/smarttube-backup.sqlite");d.close()'
```

Copy the backup out using `docker cp` and remove only that completed backup
file after it has been safely stored off-server. Automate encrypted off-VPS
backups before relying on sync for important personal preferences.

### Updates and rollback

Rebuild with `docker compose up -d --build` after pulling tested code. The
service uses the same schema and HTTP API as the existing app, and CI checks
both providers' shared handler tests. Preserve a known-good image tag and a
pre-upgrade SQLite backup for server rollback. The phone and TV APKs have their
own independent signed update and recovery workflows.

### Limitations

- Search and channel discovery can still depend on API.SH when Rumble's site
  blocks a listing. Saved listings and Editor's Picks help when requests are limited.
- This is a single-account sync service intended for Pat's own phone/TV
  devices. Do not present it as a public multi-user platform.
- The HTTP service itself is deliberately unencrypted on localhost; only
  expose the public DNS name through a correctly configured HTTPS proxy.
- VPS deployment and public endpoint activation have **not** happened until
  access to the host, DNS and proxy configuration are confirmed.
